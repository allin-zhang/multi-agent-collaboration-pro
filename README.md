# 多 Agent 协作开发工作流

> Skill slug：`multi-agent-collaboration-pro`  
> 一个人带 10 个 Agent，Multi 是今年互联网打工仔的版本答案。

这是一套面向产品 Owner、非工程师、独立开发者和小团队的 **Multi-agent Collaboration** 工作流。

它适合用于 MVP 开发、代码修改、内容生产、技术债处理和复杂任务交付，提供一套人在回路的需求拆解、任务编排、执行范围控制与 Code Review 方法。

核心原则：

> 人决定方向，多 Agent 协作；编排型 AI 拆任务和控范围，执行 Agent 只做明确小任务，最后由人验收。

---

## 这个 Skill 解决什么问题

很多人用 AI 做产品或写代码时，会直接把一个大需求丢给 Agent：

```text
帮我优化一下这个页面。
帮我修一下这个 bug。
帮我把这个功能做完整。
```

这类指令看起来省事，但很容易带来几个问题：

| 问题 | 结果 |
|---|---|
| 需求太模糊 | Agent 自己猜，容易跑偏 |
| 一个任务塞太多目标 | diff 变大，review 成本升高 |
| 没有限定修改范围 | Agent 容易顺手重构、乱改文件 |
| 自动检查替代真实验收 | 代码通过了，但体验不一定对 |
| 技术债和业务需求混做 | 小补丁变成大改动，风险变高 |

这个 Skill 的作用，就是把这些不稳定的 AI 协作过程拆开：

```text
用户 / Owner 定方向
→ 编排型 AI 拆方案、写任务、控范围、做 review
→ 执行 Agent 按原子任务交付
→ 用户做真实环境验收
```

---

## 适用人群

| 人群 | 适用原因 |
|---|---|
| 产品 Owner | 有产品判断，需要把想法拆成可执行任务 |
| 非工程师 | 不想直接读完整代码，但希望能推进 MVP |
| 独立开发者 | 想提高开发效率，又不想让 Agent 把项目改乱 |
| 小团队 | 需要一套轻量的 AI 协作流程，而不是重流程管理 |
| 内容创作者 / 运营 | 有内容和场景，需要把想法变成产品、脚本或交付物 |
| AI Agent 使用者 | 想降低多 Agent 协作时的返工和上下文成本 |

---

## 适用场景

- MVP 从 0 到 1 拆解。
- 已有项目的小步迭代。
- 代码 bug 诊断与小补丁任务编排。
- 执行 Agent 改完后的 Code Review。
- 技术债识别、登记和独立处理。
- 内容生产流程拆解。
- 多个 AI / Agent 协同完成复杂任务。
- 把个人协作经验沉淀成团队工作流。

---

## 不适用场景

这个 Skill 不适合下面这些情况：

- 完全无人监督的自动执行。
- 高风险生产变更直接交给 Agent 修改。
- 用户不参与方案确认和最终验收。
- 需求本身还没想清楚，却希望执行 Agent 自动补完全部产品判断。
- 一次性大范围重构，且不打算拆成多个小任务。

它不是让 AI “自动替你负责”。

它更像是一套协作护栏：让人保留判断，让 Agent 专注执行。

## 角色分工

| 角色 | 职责 | 不负责 |
|---|---|---|
| Owner / 用户 | 定方向、给约束、确认方案、做真实验收、决定是否收口 | 不需要亲自写完整代码或读完整大 diff |
| 编排型 AI | 澄清需求、拆方案、评估工作量、写原子任务、审查执行结果、维护沉淀 | 不在用户未确认时直接推动大改 |
| 执行 Agent | 按任务单改代码、产出内容、跑检查、返回摘要 | 不做开放式探索、不顺手重构、不扩大范围 |

如果只有一个 AI，也建议在流程上拆分“编排阶段”和“执行阶段”。

不要让同一个上下文里边想边改。这样最容易让任务范围失控。

---

## 标准工作流

```text
1. 用户提出需求 / bug / 想法
2. 编排型 AI 判断任务类型
3. 编排型 AI 做澄清、诊断或方案对比
4. 用户确认方案或最小目标
5. 编排型 AI 写原子任务
6. 执行 Agent 按任务单执行
7. 执行 Agent 返回修改列表、摘要、自测结果和风险
8. 编排型 AI 做 Code Review
9. 用户做真实环境验收
10. 通过则收口；不通过则补小任务；必要时登记技术债 / 决策
```

其中最重要的是第 4、8、9 步：

| 步骤 | 为什么重要 |
|---|---|
| 用户确认方案 | 避免 AI 自己做产品取舍 |
| Code Review | 挡住范围失控、无关重构和边界风险 |
| 真实环境验收 | 自动检查通过，不等于体验通过 |

## 任务类型怎么判断

| 类型 | 编排方式 | 产出 |
|---|---|---|
| 新需求 / 想法 | 拆模块，列 2～3 个方案，评估 XS/S/M/L、风险、扩展性 | 推荐方案 + 待确认 |
| Bug / 异常 | 先无代码诊断，列可能原因和低成本验证步骤 | 根因判断 + 小补丁任务 |
| 执行结果 / diff | 做 Code Review，标必改/建议/可选/通过 | 审查表 + 后续任务 |
| 技术债 | 判断是否影响当前目标；能不顺手做就先记录 | 技术债条目或独立任务 |
| 数据/配置维护 | 精确到 ID、字段、文件、校验命令 | 小范围修改任务 |
| 文档/方法论沉淀 | 抽象为通用模板，去掉项目私有细节 | 协作文档 / 模板 / Skill |

## 工作量分级

| 规模 | 判断标准 | 推荐处理 |
|---|---|---|
| XS | 1～10 行或单点文案 / 逻辑修复 | 可直接给原子任务 |
| S | 10～50 行，局部逻辑或小功能 | 明确验收路径后执行 |
| M | 50～150 行，跨文件或交互链路 | 先给方案，再拆成多个任务 |
| L | 150 行以上、跨模块或架构变更 | 必须拆分；不要一次交给执行 Agent |

一个很实用的判断：

> 预估 diff 超过 50 行时，先解释思路，再拆任务。

## 原子任务模板

给执行 Agent 的任务必须是原子任务。

模板如下：

```text
【一、任务背景与目标】

说明当前问题是什么、为什么要改、希望达到什么效果。

【二、修改范围】

只允许修改：
- path/to/file-a
- path/to/file-b

不要修改：
- path/to/unrelated-file
- 数据文件 / 样式文件 / 配置文件 / 文档，除非本任务明确要求

【三、具体修改要求】

1. 明确第一项修改，尽量精确到函数名、变量名、组件名、字段名或数据 ID。
2. 明确第二项修改。
3. 明确兼容旧数据、旧路径或异常输入的要求。

【四、限制与注意事项】

1. 不要重构无关代码。
2. 不要扩大修改范围。
3. 不要顺手处理技术债。
4. 不要改变已有用户路径，除非任务明确要求。
5. 如果发现任务外问题，只记录，不要修改。

【五、验收标准】

1. 验收点 1。
2. 验收点 2。
3. 涉及 UI / 交互 / 状态恢复 / 外部系统时，列出真实环境验证路径。

【六、自测命令或检查方式】

根据项目类型填写，例如：
- 语法检查
- 单元测试
- 数据校验脚本
- 构建命令
- 手动检查路径

【七、输出要求】

完成后只输出：
1. 修改文件列表
2. 关键改动摘要
3. 自测结果
4. 风险点
5. 是否修改了禁止修改的范围
6. 建议的人工验证路径

不要贴完整大文件内容。
```

## Code Review 模板

执行 Agent 交付后，不要直接收。

建议按这个表格审查：

```markdown
| # | 位置 | 等级 | 问题 | 建议 |
|---|---|---|---|---|
| 1 | 文件/函数/模块 | 必改/建议/可选/通过 | 说明问题 | 给出建议 |
```

等级说明：

| 等级 | 含义 |
|---|---|
| 必改 | 不改会导致 bug、数据污染、主链路异常、安全风险或明显体验问题 |
| 建议 | 质量或维护性问题，可以择机处理 |
| 可选 | 可做可不做，不影响当前任务 |
| 通过 | 当前项无问题 |

重点检查：

- 是否只改指定范围。
- 是否新增未说明的文件。
- 是否出现无关重构。
- 是否影响核心用户路径。
- 是否影响已有数据结构。
- 是否兼容旧数据。
- 是否处理空值、重复项、非法输入等边界。
- 是否运行必要语法检查、测试或构建。
- 是否列出人工验证路径。

## 技术债处理规则

技术债可以记录，但不要在业务任务中顺手重构。

建议状态：

| 状态 | 含义 |
|---|---|
| 待处理 | 已确认存在，后续择机处理 |
| 观察中 | 目前不处理，等规模或问题明显后再评估 |
| 已处理 | 已通过独立任务解决 |
| 放弃 | 明确不再处理 |

处理原则：

1. 当前目标不依赖的技术债，先登记。
2. CSS 合并、数据拆分、架构调整等中风险任务必须单独开。
3. “代码更好看”不等于今天要做。
4. 每次处理完技术债，要更新状态和验收结果。

## 推荐沉淀文件

对长期项目，建议在业务仓库外或独立知识目录维护协作包。

最小协作包：

| 文件 | 用途 |
|---|---|
| `AGENTS.md` | 给 AI / Agent 的项目协作规则 |
| `TASK_TEMPLATE.md` | 原子任务模板 |
| `REVIEW_CHECKLIST.md` | 审查清单 |
| `TECH_DEBT.md` | 技术债清单 |
| `DECISIONS.md` | 决策记录 |
| `PROJECT_CONTEXT.md` | 项目上下文 |

如果项目不适合建文件，也可以沉淀到 iWiki、Notion、飞书文档或其他团队知识库。

## 示例 Prompt

### 1. 拆一个新需求

```text
我想给这个产品加一个分享功能，帮我按多 Agent 协作开发工作流拆一下。
```

期望输出：

- 需求涉及模块
- 必须做 / 可以缓的部分
- 2～3 个方案
- XS/S/M/L 工作量评估
- 风险与推荐方案
- 等用户确认后，再输出执行 Agent 的原子任务

### 2. 诊断一个 bug

```text
我发现未完成任务卡片里的数量一直是 0，帮我先诊断，不要直接让 Agent 改。
```

期望输出：

- 最可能的 2～3 个原因
- 低成本验证步骤
- 可能涉及的文件或数据结构
- 确认根因后生成小补丁任务

### 3. 写执行 Agent 任务

```text
按刚才确认的方案，帮我写一条给执行 Agent 的原子任务。
```

期望输出：

- 背景与目标
- 修改范围
- 禁止范围
- 具体修改要求
- 验收标准
- 自测命令
- 输出要求

### 4. Review 执行结果

```text
这是执行 Agent 改完后的摘要，帮我 review 一下。
```

期望输出：

| # | 位置 | 等级 | 问题 | 建议 |
|---|---|---|---|---|
| 1 | 文件/函数/模块 | 必改/建议/可选/通过 | 说明问题 | 给出建议 |

### 5. 梳理技术债

```text
我们看看今天还有哪些技术债适合处理，按风险和工作量排一下。
```

期望输出：

- 技术债候选列表
- 工作量评估
- 风险评估
- 推荐执行顺序
- 不建议今天处理的项
- 如需处理，再拆一条原子任务

## 和普通 AI 写代码有什么区别

| 普通方式 | 本 Skill 的方式 |
|---|---|
| 一句话让 AI 改 | 先判断任务类型，再拆方案 |
| Agent 自己决定怎么做 | 用户确认方案后再执行 |
| 一个任务混多个目标 | 一个任务只做一个原子目标 |
| 改完直接收 | 先 Review，再真实验收 |
| 技术债顺手做 | 技术债单独登记、单独处理 |
| 上下文越聊越乱 | 用模板、清单和文档沉淀流程 |

## 注意事项

- 不要用于完全无人监督的高风险自动执行。
- 不要让执行 Agent 承担开放式产品判断。
- 不要把多个需求塞进一条任务。
- 不要把技术债和业务需求混做。
- 不要只看自动检查结果就跳过真实环境验收。

---

## 一句话总结

多 Agent 协作不是让 AI 替人负责，而是让人带着多个 AI，把混乱的需求拆成小块、边界清楚、能被 review、能被验收的交付。
